- Dynamic N-host / M-map architecture: one local Windows Manager per host, arbitrary locally owned map counts and multiple independent clusters. Authenticated LAN peers expose read-only status; only the local owner may write/start/stop its maps. The historical original Legacy Store-v1 two-host, 5+5-map session/locks/UNC data remain a strictly isolated, byte-preserved migration adapter, never a global product limit. No free-form remote start/stop writes or SQL/database inside the shipping Manager. External plugins' MariaDB remains a separate service.
- **Preserve original Store-v1 and character-travel data byte-for-byte.** No automatic `-converttostore`, conversion/rebuild, lock/session deletion, or zero-byte arkprofile cleanup. Keep historic map protection until independent, verified live integration tests are passed.
- No production ASA-server or shared Store/transfer files are used as developer test fixtures. Run CI on isolated Windows test files and do not equate its green state with live character-travel certification.
- **One supported product/version:** **Obsidian Command 2.0.0 Preview**. `desktop/Version.props` is the single version authority; .NET, React `package.json`, and Inno Setup must match or CI fails. GitHub uses `v2.0.0-obsidian-preview.<run>` as an immutable technical build marker, NOT a second user-visible version. Keep the legacy Obsidian 1.4-to-2.0 update path, the exact current `UntamedDesktop.exe` / `Untamed_Obsidian_Desktop_Preview_Setup.exe` asset and existing separate Inno AppId. Never ship a new WPF installer/release; the manual legacy workflow may only run read-only Store-v1 reference regressions. See `docs/release/OBSIDIAN-ONE-PRODUCT-VERSION-POLICY.md`.
- Do not reintroduce the abandoned SQL/MariaDB GUI, historic three-SQL archive/restore, or expose secrets in GitHub releases or the React UI.

## Mandatory P0 native runtime simplification (user decision 2026-11-26)

The authoritative new runtime refactor plan is [issue #250](https://github.com/Gunter1122cloud/untamed-manager-releases/issues/250). It supersedes earlier *runtime* operator approval / historical enrollment requirements, not data preservation, authentication or actual resource ownership invariants. The existing migration/backup safeguards must be isolated from ordinary ASA lifecycle; replace runtime gates through tested call-site migration, never blindly delete safety checks.

- Before **every implementation PR**, inspect current relevant open-source ASA manager implementation(s) and applicable ARK/ASA API documentation. Record upstream repo, exact commit SHA, file/line, proven behavior, adapted implementation, deviations and license in the PR. Reuse compatible components when license/architecture allow; otherwise implement independently. YARK GPL-3.0 compliance is mandatory if code is directly incorporated; do not silently adopt Electron/SQLite.
- Finish #250 in dependency order; one shared local per-map engine for UI, Discord, watchdog, scheduler and batches. Native `-usestore` and cluster arguments, direct/ASA API Loader. No special Kova runtime protocol; dynamic map/host roster. Preserve existing profile/transfer data byte-for-byte; conversion only as distinct explicit migration.
- No new NeedsOperator, OperatorReviewed, manual journal cleanup, duplicate approval, or unrelated host-global runtime lock. Replace stale receipt admission gates with automatic reconciliation of actual process and storage state. Terminal errors stay diagnostic, never permanently block normal commands. Prevent concurrent conflicting work on the same real resource; interrupted destructive writes require validated recovery or scoped actionable failure, not generic operator approval. Legacy state names may remain solely in backward-compatible migration readers until old formats are retired.
- Every change needs isolated native and UI regression tests, green Windows CI on exact current HEAD after conflict resolution, green main Windows/Discord CI and matched Setup/Portable/SHA256SUMS. CI is not live ASA acceptance. No claim of full implementation until #250 acceptance criteria are satisfied; #244 is an integration experiment, not the shipped engine. No production server actions without separate authorization.
